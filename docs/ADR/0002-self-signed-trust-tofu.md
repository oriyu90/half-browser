# ADR-0002: 自己署名証明書の信頼モデル（ホスト + 証明書 SHA-256 の TOFU）

- 状態: **Accepted**（2026-10-31）
- 決定者: TO-PLAN（HB-PLAN-01）
- 関連: 要件 2 / TECH-RESEARCH §1, §2 / ADR-0001, ADR-0003 / AC-10〜AC-18

## Context

自宅 LAN の `https://192.168.0.165:8844` のような自己署名証明書のサイトを、ブラウザ標準の警告で止めずに開きたい。Android System WebView では:

- `onReceivedSslError(WebView, SslErrorHandler, SslError)` が呼ばれ、アプリは `cancel()` か `proceed()` を**必ず**呼ぶ（TECH-RESEARCH §1.1）。
- `proceed()` の判断は WebView 側に**永続化されない**（§1.2）。
- 公式ドキュメントは「常に `cancel()`」「ユーザーに SSL エラーを問うな」と明記している（§1.3）。

つまり要件を満たすには、**(a) 公式推奨に反する操作を意図的に行い、(b) 永続化をアプリ側で代替する**しかない。何を信頼し、何を信頼しないかを明確に定義する必要がある。

## Decision

**「ホスト + 証明書 DER の SHA-256」を単位とする TOFU（Trust On First Use）ピン留めを採用する。**

### 信頼の単位

```kotlin
// 既存実装（app/src/main/java/com/yukiorita/halfbrowser/core/Models.kt:33）
data class TrustedSite(
    val host: String,                 // 小文字・ポートを含まない
    val fingerprintSha256: String,    // 証明書 DER の SHA-256（小文字 hex、区切り無し）
    val subject: String = "",
    val issuer: String = "",
    val addedAt: Long = 0L,
    val lastSeenAt: Long = 0L,
)
```

- 一致条件: `host.lowercase() == saved.host.lowercase()` **かつ** `fingerprintSha256 == saved.fingerprintSha256`（既存 `TrustPolicy.decide()`）。
- **ポートは信頼の単位に含めない。** 表示には `host:port` を出す。
- **証明書の DER 全体を保存しない。** SHA-256 のみ保存し、`subject` / `issuer` は表示用のコピーとして持つ（照合には使わない）。

### 判断の3値

| 判定 | 条件 | 動作 |
|---|---|---|
| `Trusted` | ホスト一致 かつ フィンガープリント一致 | **自動 `proceed()`**（ユーザー操作なし） |
| `Unknown` | ピン無し | インタースティシャル: 「今回だけ」「このサイトを常に信頼」「戻る」 |
| `Changed` | ホスト一致だがフィンガープリント不一致 | インタースティシャル（**警告強化**）。以前の Subject / 発行者 / 追加日時を併記し、差分を見せる。「常に信頼」は**明示的な再確認**（チェックボックス等の追加操作）を要求 |

### 「今回だけ」の扱い

`proceed()` を呼ぶだけで**何も保存しない**。次回の遷移・再読み込みで再び警告が出る。これは仕様であり、バグではない（UI に「この許可は保存されません」と明記する）。

### 「常に信頼」を許可しない条件

以下は**ピン留めを禁止**し、「今回だけ」と「戻る」のみ提供する。

1. **証明書の X509 が取得できない**（`getX509Certificate()` が null かつ `saveState()` フォールバックも失敗）。ハッシュできないものをピン留めしない。
2. **期限切れ／未開始**（`SSL_EXPIRED`, `SSL_DATE_INVALID`, `SSL_NOTYETVALID`）。自己署名の**更新忘れ**を「常に信頼」で固定化させない。
3. **ホスト名不一致**（`SSL_IDMISMATCH`）。証明書の SAN と URL ホストが食い違う状態を恒久化しない。
4. ピン件数が上限（50 件）に達している。

ピン可能なのは実質的に `SSL_UNTRUSTED`（信頼されていない発行者＝自己署名）と、CA 署名済みだが期限切れ等の場合の「今回だけ」である。

### 失効

設定 →「信頼済みサイト」から1件ずつ削除できる（既存 `TrustedSiteList` の削除）。削除後は次回アクセスで `Unknown` に戻る。**一括削除は提供しない**（誤操作で全ピンが消えると、以後の警告で安易に「常に信頼」を押す誘因になる）。

### 保存先とバックアップ

- `SharedPreferences` の JSON（既存 `Codecs.encodeTrustedSites` / `decodeTrustedSites`）。
- **バックアップ対象に含めない**方針は採用しない（秘密ではないため）。ただし `allowBackup` の復元でピンが戻ることの是非は、**復元後も同じ証明書なら妥当**なので許容する。
- 認証情報（ADR-0003）は**バックアップから除外**する。ここは非対称でよい。

### 事後検証（post-hoc verification）

`proceed()` の判断が WebView 側に保持される可能性（TECH-RESEARCH §1.2 の解釈 B）に備え、**二重の検知**を持つ。

1. `onPageFinished`（https・メインフレームのみ）で `WebView.getCertificate()` の SHA-256 をピンと照合する。不一致なら `stopLoading()` して `Changed` を出す（追加通信ゼロ）。
2. 「信頼済みサイト」から失効させたときは、**WebView を破棄・再生成**する（保持された判断を捨てる）。

これにより「ピンを消したのに繋がる」という最悪の失敗を防ぐ。AC-12b / AC-12c で実測する。

### 同一ホストに複数証明書を許す

`TrustedSite` の一意性は **host + fingerprint** とする（host あたり最大 8 件、全体 50 件）。

- 理由: 同一ホストの別ポートで別証明書を使う LAN 機器（`:8443` と `:9443`）で、A を信頼 → B で Changed → B を信頼 → A で Changed という**無限往復**が起きる。
- 判定: 一致するピンが1つでもあれば `Trusted`。一致せず同一ホストにピンがあれば `Changed`（`lastSeenAt` が最新のものを previous として提示）。ピンが無ければ `Unknown`。
- 既存 `TrustPolicy.decide(host, fingerprint, saved: TrustedSite?)` は残し、`decide(host, fingerprint, saved: List<TrustedSite>)` のオーバーロードを追加する（純粋関数のまま）。

## Consequences

### 守れるもの

- 初回にユーザーが承認した証明書**以外**では自動続行しない。
- 証明書が差し替わった場合（攻撃・更新の別を問わず）に**必ず再警告**する。
- 信頼の範囲はホスト単位に限定され、他ホストへ波及しない。
- 資格情報（ADR-0003）は「信頼済みまたは今回だけ許可した接続」でのみ送られる（状態機械で順序保証）。

### 守れないもの（明示するリスク）

| # | 守れないもの | 説明 | 受容判断 |
|---|---|---|---|
| R1 | **初回接続時の MITM** | TOFU の定義。初回に攻撃者の証明書を信頼すれば以後ずっと通る | 受容。初回は Subject / 発行者 / フィンガープリントを全て表示し、サーバー側の値と比較できるようコピー機能を提供 |
| R2 | **信頼後の MITM** | ピン一致＝同じ証明書。秘密鍵が盗まれれば検出不能 | 受容（自己署名の限界）。ユーザーが「常に信頼」を押した時点で、そのホストの証明書検証を実質的に無効化したことになる |
| R3 | **ユーザーの誤操作** | 「常に信頼」を反射的に押す | 緩和: 既定ボタンは「戻る」、危険色、説明文、一覧・失効導線。完全な防止は不可能 |
| R4 | **同一証明書を使う別ホスト** | 証明書の SAN が複数ホストを含む場合、別ホストでも同じ証明書なら別途ピンが必要（ホスト単位のため） | 安全側（ホストごとに承認が要る） |
| R5 | **アプリ内の他コンポーネント** | 将来 JS ブリッジや Custom Tab を追加すると信頼境界が崩れる | 制約: JS ブリッジ禁止（要件 10）。新コンポーネント追加時は本 ADR を再審 |
| R6 | **ポートの区別** | host のみで照合するため、同じホストの別ポートに同一証明書があれば自動信頼 | 受容。同一証明書＝同一秘密鍵保有者であり、リスク増分は小さい（推定） |

### 公式推奨からの逸脱（記録）

Google の公式見解は「`proceed()` するな」「ユーザーに問うな」である（TECH-RESEARCH §1.3）。本アプリは**ユーザーの明示要件に基づき逸脱する**。逸脱の正当化は「ユーザーが自分の LAN サーバーの証明書を自分で発行しており、フィンガープリントを突き合わせる能力がある」という**限定された利用シナリオ**に依存する。したがって:

- この機能は**既定で有効だが、初回必ず警告**という形を崩さない。
- 将来「警告なしで自動信頼」する設定は**追加しない**（要件にも無い）。
- README / アプリ内説明に「自己署名サイトの信頼は自己責任であり、公共 Wi-Fi では使うな」と明記する。

### 実装上の帰結

- `SslTrustCoordinator`（新規）が `SslErrorHandler` の寿命を管理する。**保留は1件のみ**、2件目は即 `cancel()`、60 秒でタイムアウト `cancel()`、`ViewModel.onCleared()` で必ず `cancel()`（TECH-RESEARCH §1.4）。
- 証明書取得は `Build.VERSION.SDK_INT >= 29` で分岐し、26–28 は `SslCertificate.saveState()` の `"x509-certificate"` バイト列を使う（§2.1）。この分岐は**1ファイルに閉じ込め**、ユニットテストは純粋関数側で行う。
- `TrustPolicy.decide()` は既存実装をそのまま使う（変更不要）。ピン上限・期限切れ拒否は**呼び出し側のポリシー**として追加する（`TrustPolicy` は純粋な照合に保つ）。

## Alternatives

### A. 証明書を一切保存せず、毎回インタースティシャル

- 利点: 実装最小、状態無し。
- 欠点: 自宅サーバーを開くたびに3タップ要求され、要件「常に信頼」を満たさない。
- 不採用。

### B. ホスト単位で「すべての証明書を許可」

- 利点: 証明書更新で再警告が出ない。
- 欠点: **証明書変更を検出できなくなる**（TOFU の意味が消える）。要件「証明書が変わったら再警告」に反する。
- 不採用（決定的）。

### C. 証明書 DER 全体を保存して完全一致を取る

- 利点: SHA-256 衝突の心配が皆無。
- 欠点: 保存サイズ増（1件 1–2KB）、JSON が膨らむ、比較ロジックが複雑。SHA-256 の衝突耐性で実用上十分。
- 不採用（SHA-256 のみ）。

### D. ユーザーが CA 証明書を端末にインストールする運用

- 利点: WebView が正規の検証を通るため、`proceed()` が不要。公式推奨に沿う。
- 欠点: 端末設定の操作が必要で、要件の「アプリ内で完結」に反する。ユーザー証明書を入れると**全アプリ**がそれを信頼するため影響範囲が広い。
- 不採用。ただし README で**より安全な代替**として紹介する（誠実さのため）。

### E. ネットワークセキュリティ設定（`network_security_config.xml`）に固定ピンを書く

- 利点: 宣言的で強力。
- 欠点: **動的にユーザーが追加できない**（APK に埋め込む必要がある）。要件 2 の「常に信頼」を UI から行う要件に合わない。
- 不採用。

## Status

**Accepted**。R1/R2 は受容済みリスクとして README とアプリ内注記に明記する。将来 Android が WebView に証明書例外の公式 API を追加した場合、本 ADR を Superseded にする。
