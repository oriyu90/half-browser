# v1.8.0 計画 — VPN の接続安定性とホーム画面の状態表示

- 日付: 2026-11-11
- 対象: `oriyu90/half-browser`（Android）
- 関連: ADR-0018（アプリ内 WireGuard VPN）、ADR-0022（本版の再設計）

## 1. 報告された問題

1. VPN を導入して、Half-Browser で VPN 先のサイトを開こうとすると繋がらずタイムアウトする。
2. VPN を繋いだままスリープ等でしばらく経つと、UI 上は「接続中」のままなのに VPN 先へ繋がらない。
   → アプリを開き直すたびに確認し、繋がっていなければ再接続したい。
3. ホーム画面に VPN の接続状態が分かる表示が欲しい。

## 2. 現状分析（v1.6.1 のコード）

### 2-1. 「接続中」の意味がトンネル UP だけだった

`VpnController` は `GoBackend.setState(UP)` が成功した時点で `VpnState.Connected` にしていた。
これは「TUN デバイスが作られ、ルーティングが入った」ことしか意味しない。
WireGuard のハンドシェイク（サーバーとの鍵交換）は非同期に行われ、
失敗しても `setState` は成功したままになる。したがって:

- UDP 51820 が塞がれている / サーバーが落ちている / サーバー側の鍵が不一致
  → アプリは「接続中」と表示し続けるが、実際には何も流れない。
- スリープ復帰後、NAT / サーバーのセッションが失効しても、TUN は残るので「接続中」のまま。
  `PersistentKeepalive` が無い設定ではアイドル後に NAT マッピングが消え、
  次の通信がサーバーに届かない（症状 2 の主因）。

### 2-2. スリープ復帰時に何も検証していなかった

`MainActivity` には `onStart`/`onStop` のフックが無く、VPN の状態はプロセス内の
`StateFlow` だけが真実だった。復帰時にも、バックグラウンド中にも、
ハンドシェイクの鮮度を確認する処理が無かった。

### 2-3. ハンドシェイク状態を取得する手段が無かった

`Backend.getStatistics(tunnel)` は `Statistics`（ピアごとの rx/tx と
`latestHandshakeEpochMillis`）を返すが、アプリはこれを使っていなかった。

### 2-4. タイムアウト時に原因を案内する経路が無かった

`onReceivedError` は汎用のネットワークエラー画面を出すだけで、
「VPN 接続中に失敗した」ことを利用者に伝えず、再接続の導線も無かった。

### 2-5. ホーム画面の状態表示が小さすぎた

`HomeVpnPanel` の 1 行は「ドット + ラベル」だけで、ハンドシェイクの有無・
最終確認時刻・失敗理由の詳細を確認する手段が無かった（症状 3）。

### 2-6. 設定の既定値が症状 2 を助長していた

`vpnAutoConnect` の既定値は `false`。アプリを開き直しても再接続しない。

## 3. 設計方針

1. **状態を「トンネル」と「疎通」に分ける。**
   - トンネル: `Disconnected / Connecting / Connected / Disconnecting / Failed`
   - 疎通: `Unknown / Verifying / Healthy / Stale / Unreachable`
   - `Connected` は「トンネルが上がっている」、`Healthy` は「直近のハンドシェイクが新しい」。
   - UI は 2 つを組み合わせて表示する（例:「接続中（確認中）」「接続中（応答なし）」）。
2. **ハンドシェイクの鮮度で判定する。** `getStatistics` の
   `latestHandshakeEpochMillis` を使い、閾値は次のとおり（純粋ロジックでテスト）:
   - `Verifying`: UP 直後、ハンドシェイク待ちの猶予（45 秒 = `HANDSHAKE_GRACE_MS`）
   - `Healthy`: 最終ハンドシェイクが 180 秒以内（`HEALTHY_WINDOW_MS`）、かつ UP 以降のもの
   - `Stale`: 最終ハンドシェイクが 180 秒より古い（または一度も無い）
   - `Unreachable`: 一度もハンドシェイクできずに 45 秒経過
3. **アプリ復帰時（onStart）に必ず再検証する。**
   - トンネルが残っていて Healthy → そのまま。
   - Stale / Unreachable → 自動で再接続（設定 `vpnAutoReconnect` が ON のとき。既定 ON）。
   - トンネルが消えている（プロセス再生成・OS による停止）→ 再確立。
   - システム VPN 同意が既にある場合のみ自動再接続する（ダイアログを勝手に出さない）。
4. **バックグラウンドでも監視する。** WorkManager の定期 Worker（15 分〜）で
   ハンドシェイク鮮度を記録し、失効していれば再接続を試みる（同意済み・設定 ON のみ）。
5. **再接続の競合を世代番号で防ぐ。** `VpnController` の非同期処理に世代を持たせ、
   古い世代の結果が新しい状態を上書きしないようにする（クラッシュ安全性・状態整合）。
6. **設定の互換性。** 既存の `vpnAutoConnect` は「起動時に接続」として残し、
   新規 `vpnAutoReconnect`（復帰時に検証して再接続、既定 ON）を追加する。
   既存プロファイル・バックアップ形式は変更しない。
7. **秘密情報を増やさない。** 状態履歴（最終ハンドシェイク時刻・最終確認時刻・結果）は
   平文の SharedPreferences に保存してよい（鍵・IP・DNS は保存しない）。
   バックアップ対象外にする。
8. **日英両方の文字列を追加し、キー一致テストで担保する。**

## 5. 停止条件・検証

- JVM テスト全件成功、lint 0 errors、日英キー一致。
- エミュレータ（API 34）で: 接続→ハンドシェイク無しで「応答なし」表示、
  復帰時の再検証と自動再接続、ホームのバッジと詳細シート、タイムアウト時のヒント。
- release（R8）ビルドで起動・VPN パネル・Worker の登録を確認。

## 6. 既知の限界（正直な記録）

- エミュレータのユーザーネットでは protect 済み UDP がホストに届かず、
  実際のハンドシェイク成功（Healthy）は再現できない（v1.6.0 と同じ制約）。
  Healthy の判定は JVM テストと、ハンドシェイク時刻を注入した検証で担保する。
- WorkManager の周期実行は OS が最短 15 分に丸める。即時性は onStart の再検証が担う。
