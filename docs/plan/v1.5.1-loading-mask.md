# v1.5.1 実装計画：ダークモードの読み込み中ホワイトアウトをブラックに

作成日: 2026-11-02 / 対象: Half-Browser 1.5.1

## 1. 現状の調査分析（一次情報: コード + git 履歴）

### 現象
ダークモードでページを開いた直後（読み込み中）、画面が一瞬白くなる。

### 原因の特定
| 事実 | 根拠 |
|---|---|
| WebView の表面色は **明示的に白** | `BrowserScreen.kt` WebViewHost: `backgroundColor = Color.WHITE`（factory 内 `setBackgroundColor`）＋ `configureWebView` 内でも `setBackgroundColor(WHITE)` |
| 白が選ばれた理由 | 1.0.0 (95ae3c6) のコメント: 「Page surface stays white, like desktop browsers. Painting it with the app's dark surface made ordinary pages (black text, no background) unreadable.」＝背景を指定しないページ（黒文字）が、暗い表面では読めない |
| ダークのアプリ背景は純黒 | `Color.kt`: DarkBackground/DarkSurface = #000000（v1.2.0 で true black 化）。windowBackground（night）= #0B1220 |
| WebView の暗化設定と背景 | `setAlgorithmicDarkeningAllowed` は設定されるが、その表示タイミングは未検証。読み込み前の WebView 背景は明示的に白 |
| 読み込み中の状態遷移 | `loadWhenSized` でレイアウト確定まで loadUrl を遅延 → その間も白い WebView が見える。`onPageStarted` → （白） → `onPageCommitVisible` → ページ描画 |
| 既存フック | `HalfBrowserWebViewClient.onPageCommitVisible` は存在する（認証キャッシュクリアで使用中）。API 26+（minSdk 26 で全端末で利用可） |

### 影響範囲
- 初回読み込み（ホーム→ブックマーク開く、外部リンク起動）
- WebView 再生成時（証明書失効、レンダラ死亡 → `state.generation` 変更）
- 既存 WebView 内の遷移・再読込でも白画面が生じる可能性があるため、各読み込み開始時にもマスクを表示する。

## 2. 実装案の比較

### 案A: WebView 背景をテーマ依存に（ダークなら黒）
- `setBackgroundColor(if (darkTheme) BLACK else WHITE)`
- **却下**: 背景指定のないページ（透明）が黒表面＋黒文字で読めなくなる。1.0.0 で実際に経験済みの回帰（算法暗化があっても同様）。

### 案B: 読み込みマスク（採用）
- WebView の表面は白のまま（ページ可読性は現状維持）。
- WebView の上に Compose でマスク層を重ね、初期表示と各ページ読み込み開始から表示準備通知まで表示する。
- ダーク時だけ純黒マスクを重ね、ライト時はマスクを表示せず従来の WebView をそのまま使う。
- `onPageCommitVisible` または `onPageFinished` 後に `postVisualStateCallback` を要求し、その描画可能通知でマスクを解除する。コールバックは描画可能な状態を示し、ディスプレイへの表示完了まで保証するものではない。
- アプリ内の再読み込み・ブックマーク切替は要求時にマスクし、各 `onPageStarted` でも再表示する。フラグメントのみの移動は開始通知がない場合があるため、要求時のマスクを表示しない。最新の開始 URL と世代に一致する描画準備通知で解除する。

### 案C: CSS 注入で body 背景を黒化
- ページ CSS を書き換える系は v1.3.0 で DSH を壊した前科あり。**却下**。

## 3. 採用設計（案B）

```
WebViewHost の generation ごとの Compose 状態 pageReady と loadingUrl
  WebView生成時              → false
  onPageStarted              → false、URL を記録
  onPageCommitVisible / onPageFinished → URL が一致する場合に描画準備通知を要求
  描画準備通知               → 世代が一致する場合 true

WebViewHost の Box:
  AndroidView (白表面のまま)
  if (darkTheme && (!pageReady || pageLoadRequested)) Box(黒で fillMaxSize)
```

- マスクは `darkTheme && (!pageReady || pageLoadRequested)` の場合のみ `Color.Black`。
- エラーペインはマスクより後（手前）に描画される既存順序を維持
- `darkTheme` は既に WebViewHost に渡っている（Compose 側で再合成されるのでマスク色は追従）

### 明示的に変えないもの
- WebView 表面の白（案Aの回帰回避）
- ライトモードの表示（マスクは表示しない）
- ページの HTML や CSS（ただしダーク時の遷移中は旧ページを黒いマスクで覆う）

### 既知の関連問題（本件スコープ外、記録のみ）
- 開いているページでテーマを切り替えても `update = { }` のため算法暗化が再適用されない（次回ナビゲーションまで）。マスク色は Compose 側なので追従する。

## 検証途中の記録（2026-11-02）

- API 34 エミュレータ、遅延 HTTP ページで、初回読み込み中の中央画素はダーク `#000000`、ライト `#ffffff`。読み込み後にページ文字列と非黒画素を確認。
- 再読み込みではサーバー応答前に `onPageStarted` が届かず、旧ページが見えていた。要求時からマスクする修正後、60秒遅延の再読み込み中に中央画素が黒、応答後に白いページと文字列が見えることを確認。
- `:app:testDebugUnitTest :app:lintDebug :app:assembleDebug` 成功、単体テスト 124 件・失敗 0（2 件はナビゲーション世代のテスト）。
- 接続拒否時にはエラー説明と Retry が、HTTP 302 後には遷移先の本文が表示されることを確認。DSH は未検証。背景色未指定のサンプルでは HTML の文字列と白い背景が表示されたが、人間による可読性の目視検証は未実施。

## 5. リスク
- `onPageCommitVisible` が呼ばれない場合にも `onPageFinished` 後に描画準備通知を要求する。どちらも発火しない場合や描画準備通知が届かない場合はマスクが残る可能性がある。エラーペインはマスクより前面に表示される。
- マスク表示が初回コミットまで長引く場合（重いページ）は「黒いまま時間がかかる」ように見えるが、要件はまさにそれ（白ではなく黒）。
