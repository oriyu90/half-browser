# v1.9.0 計画 — バックグラウンド安定性と省電力

- 日付: 2026-11-11
- 対象: `oriyu90/half-browser`（Android）、現行 `v1.8.0`（`ed93612`）
- 関連: ADR-0018（アプリ内 WireGuard VPN）、ADR-0021（Always-on VPN）、
  ADR-0022（疎通検証・復帰時再接続）
- 目的: **バックグラウンドでの安定動作**（眠っていても・再起動しても・ネットワークが
  切り替わっても VPN が壊れたままにならない）と **省電力**（起きている時間と通信を減らす）
  を、実測に基づいて両立させる。

---

## 1. 現行設計の精査

### 1.1 調査方法

コードを読むだけでなく、次の実測を行った（すべてこのリポジトリの現行ビルド）。

| 調べたこと | 方法 | 結果 |
|---|---|---|
| `getStatistics` の実コスト | WireGuard ライブラリのバイトコードを `javap -c` で逆アセンブル | 呼ぶたびに **ネイティブ `wgGetConfig(handle)` → 設定全体を文字列で取得 → `split("\n")` → 行ごとに `startsWith` 判定**。`Statistics` オブジェクトも毎回新規生成 |
| `getRunningTunnelNames` のコスト | 同上 | **ネイティブ呼び出しなし**。`currentTunnel` が非 null なら名前 1 件の `ArraySet` を返すだけ |
| `GoBackend` の状態の所在 | `javap -p` でフィールドを確認 | `currentTunnel` / `currentTunnelHandle` は **インスタンスフィールド**（`static` は `alwaysOnCallback` と `vpnService` のみ）。→ 別インスタンスからはトンネルが見えない |
| プロセスの生存 | `dumpsys activity processes` | VPN 接続中は 21 時間プロセスが生存、`lastActivityTime` は 1 時間 59 分前（キャッシュ済み） |
| WorkManager ジョブの制約 | `dumpsys jobscheduler` | `Requires: charging=false batteryNotLow=false deviceIdle=false` — **VPN の周期ジョブには節電系の制約が一切ない** |
| keepalive の通信量 | パケット長から計算 | 25 秒間隔で IPv4 76 B/pkt → **約 10.7 KiB/時（0.25 MiB/日）**、IPv6 で 0.32 MiB/日 |
| ネットワーク変化の扱い | `grep ConnectivityManager` | **該当なし**（ネットワーク切替を検知するコードが存在しない） |
| VPN ネットワークの可視性 | `dumpsys connectivity`（VPN 接続中） | `Transports: WIFI|VPN` のネットワークが存在し、**`OwnerUid: 10193`**（= アプリの UID）と `AdminUids: [10193]` を持つ。→ §3.3 の生存確認が実装可能 |
| 画面消灯と `onStop` | `MainActivity` のオーバーライド確認 | `onStart` / `onStop` のみ。**`onStop` は画面消灯では呼ばれない**ため、消灯中もポーリングが止まらない |

### 1.2 API 契約の検証（一次情報）

本セッションでは Web 検索・取得が利用できなかった（`DEEPSEEK_API_KEY` 未設定／fetch モジュール欠落）ため、
**端末にインストール済みの SDK スタブ（`android.jar`, API 36）と実際に使うライブラリの
バイトコード**を一次情報として検証した。これは「API が存在し、そのシグネチャがどうなっているか」
を保証する点で Web のリファレンスと同等以上に確実である（バージョンは固定）。

| 前提 | 検証方法 | 結果 |
|---|---|---|
| VPN ネットワークの所有者 UID が取れる | `javap` on `android.net.NetworkCapabilities` | `public int getOwnerUid()` と `TRANSPORT_VPN` が存在 |
| 全ネットワークを列挙できる | `javap` on `android.net.ConnectivityManager` | `getAllNetworks()` / `getNetworkCapabilities(Network)` が存在 |
| 既定ネットワークの変化を購読できる | 同上 | `registerDefaultNetworkCallback(NetworkCallback)` が存在 |
| 非公開ブロードキャストを受けられる | `javap` on `android.content.Context` | `RECEIVER_NOT_EXPORTED` 定数が存在（API 33+） |
| 電池残量制約を付けられる | `javap` on `androidx.work.Constraints$Builder`（2.10.1） | `setRequiresBatteryNotLow` / `setRequiresDeviceIdle` / `setRequiresCharging` が存在 |
| VPN ネットワークに owner UID が実際に載る | 実機（エミュレータ）で `dumpsys connectivity` | `Transports: WIFI|VPN` に `OwnerUid: 10193`（= アプリ UID）、`AdminUids: [10193]` |

**API レベルの注意**: `getOwnerUid()` は API 29 以降。`minSdk` は 26 なので、
26–28 では「不明」を返すフォールバックが必要（§3.3）。`RECEIVER_NOT_EXPORTED` は API 33 以降。

### 1.2 見つかった問題

#### A. 省電力

**A-1. 画面消灯中も 5 秒周期のポーリングが続く（最重要）**

`VpnController` は `MainActivity.onStart()` で `startPolling()` を呼び、`onStop()` で止める。
しかし `onStop()` は**画面が消灯しただけでは呼ばれない**（Activity は `onPause` までで
`onStart` 状態のまま）。したがって「VPN 接続中のまま画面を消してポケットに入れる」と、
5 秒ごとに以下が走り続ける。

- `getStatistics()` = ネイティブ `wgGetConfig` + 文字列分割 + 行走査（毎回）
- `getRunningTunnelNames()` = ネイティブなし（軽い）
- `_health` / `_reachability` の `StateFlow` 更新（値が変わらなくても `copy()` で新インスタンス）
- `healthStore.recordCheck()` = **SharedPreferences の `commit()`（同期ディスク書き込み）を 5 秒ごと**

1 時間あたり 720 回。画面が消えている間ずっと続く。これは電池にも書き込み寿命にも悪い。
`startPolling()` は「状態が Connected の間ずっと」動く設計で、可視性を条件にしていない。

**A-2. VPN の周期ジョブに節電制約がない**

`VpnHealthScheduler` は `NetworkType.CONNECTED` だけを要求し、`setRequiresBatteryNotLow` も
`setRequiresDeviceIdle` も付けていない。15 分ごとに必ず起きる。VPN が繋がっていない
（ユーザーが切断した・プロファイルが無い）ときも、`hasProfile && autoReconnect` の条件だけで
登録され続けるため、**使っていないのに 15 分ごとに起きる**。

**A-3. 変化が無いときも StateFlow を更新する**

`verifyNow()` は値が同じでも `_health.value = snapshot` を代入する。Compose 側は
`collectAsStateWithLifecycle` で購読しているので、5 秒ごとに再コンポーズが走る
（画面表示中は実害が小さいが、無駄な仕事である）。

**A-4. keepalive は常時 25 秒**

NAT 越えの正しさのため既定 25 秒は妥当だが、**画面が消えていて通信が無い間**は
もう少し緩くても NAT は保たれる（一般的な UDP NAT のタイムアウトは 30 秒〜数分）。
ここは「正しさ」とのトレードオフなので、**既定は変えず、選択肢として提示する**（§3.4）。

#### B. バックグラウンド安定性

**B-1. ネットワーク切替に追従しない（症状の主因候補）**

Wi-Fi → モバイル、モバイル → Wi-Fi、機内モードの往復、VPN サーバーの IP 変更。
いずれも**エンドポイントの解決結果と UDP の送信元アドレスが変わる**ため、WireGuard は
ハンドシェイクをやり直す必要がある。現行コードは `ConnectivityManager` を一切見ていないので、
この再接続は「次の 5 秒ポーリングが STALE と判定する」か「アプリを開き直す」まで起きない。
画面消灯中は A-1 のポーリングが動いているので偶然直ることもあるが、それは
**電池を燃やして偶然直している**だけである。

**B-2. バックグラウンド Worker は「プロセスが生きている」前提**

`VpnHealthWorker` は `container.vpn.verifyForBackground()` を呼ぶ。`VpnController` の
`backend` / `activeTunnel` はメモリ上にしかないため、プロセスが死んだ後に Worker が
最初に走ると `_state` は `Disconnected` で、`adoptExistingTunnel()` も
`runningTunnelNames` が空で失敗する。その結果 `connect()` を呼ぶが、`connect()` は
`VpnService.prepare()` を経由するため**同意が無ければ失敗**し、同意があっても
TUN を作り直すことになる。つまり Worker は「プロセスが生きている」場合しか実質仕事を
しておらず、**プロセスが死んだ場合は「再接続したつもり」で終わる**ことがある。

**B-3. ポーリングの粒度が粗い（判定に必要な情報に対して過剰）**

`VpnHealthRules` が使うのは「最終ハンドシェイク時刻」1 つだけ。健全窓は 180 秒、
猶予は 45 秒。**5 秒間隔は 180 秒窓に対して 36 倍の過剰サンプリング**である。
判定の分解能は 15〜30 秒で十分で、しかも `getStatistics` は毎回ネイティブ呼び出しを伴う。

**B-4. 画面消灯中に「壊れた」ことに気づけない**

A-1 のポーリングは動いているが、その結果は UI にしか出ない。画面消灯中に切断された場合、
ユーザーが次にアプリを開くまで分からない。**検知と復旧を分離**すべきである
（検知は安く・イベント駆動で、復旧は必要なときだけ）。

**B-5. プロセス再生成後、VPN が実際には生きているのに「切断」と表示する**

`runningTunnelNames` がプロセスメモリ由来なので、プロセスが死んで再生成されても
OS 側の VpnService は生きている可能性がある（A-1 の観測では 21 時間生存）。
しかし `adoptExistingTunnel()` は必ず失敗し、無条件に `connect()` する。
`connect()` は「まず DOWN にしてから UP」なので、**生きているトンネルを一度壊して作り直す**。
動いてはいるが、無駄な切断とハンドシェイクのやり直しが発生する。

**B-6. `KeepAliveService` が `START_STICKY`**

Web 通知の即時配信のためだけのフォアグラウンドサービスが `START_STICKY` なので、
システムに殺されると再生成される。ユーザーがブラウザ画面を閉じたのに通知だけ残る
ケースは `BrowserScreen` の `LaunchedEffect` で止めているが、プロセスが殺された場合は
`START_STICKY` の再生成が先に走りうる。

### 1.3 問題の整理

| 問題 | 分類 | 影響 |
|---|---|---|
| A-1 消灯中の 5 秒ポーリング | 省電力 | **大**（720 回/時のネイティブ呼び出し + ディスク書き込み） |
| A-2 制約なしの周期ジョブ | 省電力 | 中（未使用時も 96 回/日） |
| A-3 無変化の StateFlow 更新 | 省電力 | 小 |
| A-4 keepalive 常時 25 秒 | 省電力 | 小（0.25 MiB/日） |
| B-1 ネットワーク切替に無追従 | 安定性 | **大**（報告された症状の主因候補） |
| B-2 Worker がプロセス生存前提 | 安定性 | 中 |
| B-3 過剰なサンプリング | 両方 | 中 |
| B-4 消灯中の検知不能 | 安定性 | 中 |
| B-5 再生成で無駄な作り直し | 安定性 | 小 |
| B-6 KeepAlive の STICKY | 安定性 | 小 |

## 2. 設計方針

**「安く検知し、必要なときだけ高く払う」**

1. **イベント駆動を最優先**にする。ネットワーク変化・画面消灯・プロセス再生成という
   *実際に壊れる瞬間* に反応する。時間ベースのポーリングはその補助に下げる。
2. **可視性でコストを変える**。画面が見えている間は速く（UI の即時性）、
   消えている間は遅く（電池）、完全に止めるのではなく**イベントで起きる**。
3. **判定に必要な分解能まで間隔を落とす**。180 秒窓に対して 5 秒は過剰。
4. **プロセス再生成を「正常系」として扱う**。トンネルが OS 側で生きているかを
   ネイティブに問い合わせ、生きていれば作り直さない。
5. **節電制約を素直に付ける**。ただし「VPN を守る」仕事は電池残量で止めてはいけない
   部分があるので、**どの仕事にどの制約を付けるかを分ける**。

## 3. 実装案

### 3.1 ポーリングを「可視性 + バックオフ」に変える（A-1, A-3, B-3）

`VpnController` に明示的な可視性フラグを持たせ、間隔を段階化する。

```kotlin
// core/VpnHealth.kt に追加
object VpnHealthRules {
    /** 画面が前面にある間の確認間隔（UI の即時性を優先）。 */
    const val POLL_FOREGROUND_MS = 10_000L

    /** 画面が消えている/背面にある間の下限間隔。 */
    const val POLL_BACKGROUND_MIN_MS = 60_000L

    /** 画面が消えている間の上限（ここまで間引く）。 */
    const val POLL_BACKGROUND_MAX_MS = 300_000L

    /**
     * 次の確認までの待ち時間。
     * 疎通が健全なほど間引き、壊れている疑いがあるほど詰める。
     */
    fun nextPollDelayMs(
        foreground: Boolean,
        reachability: VpnReachability,
        consecutiveHealthy: Int,
    ): Long
}
```

- 前面: 10 秒固定（UI の数字が古くならない程度）。
- 背面: 60 秒から始め、健全が続くたびに ×1.5（上限 300 秒）。
  `STALE` / `UNREACHABLE` に落ちたら 60 秒に戻す。
- **画面消灯（`ACTION_SCREEN_OFF`）を検知したら即座に背面モードへ**切り替える。
  これが A-1 の直接の修正になる。

`verifyNow()` は**値が変わったときだけ** `_health.value` を代入する（A-3）。

**効果**: 消灯中の呼び出し回数が 720 回/時 → 12〜60 回/時（**92〜98% 削減**）。

### 3.2 ネットワーク変化で即座に再検証する（B-1）

`ConnectivityManager.registerDefaultNetworkCallback` を使い、**アプリ全体で 1 つ**の
コールバックを `HalfBrowserApplication` で登録する（Activity ではなく Application に
持たせることで、画面が無い間も動く）。

```kotlin
// data/NetworkWatcher.kt（新規）
class NetworkWatcher(context: Context, private val onChanged: (NetworkEvent) -> Unit) {
    fun start()   // registerDefaultNetworkCallback
    fun stop()
}
```

- `onAvailable` / `onLost` / `onCapabilitiesChanged` を受けたら、**1.5 秒デバウンス**して
  `VpnController.onNetworkChanged()` を呼ぶ（Wi-Fi とモバイルが同時に切り替わる瞬間に
  何度も再接続しないため）。
- `onNetworkChanged()` は「疎通を 1 回確認し、`STALE`/`UNREACHABLE` なら即再接続」。
  ネットワークが変わった直後はハンドシェイクがまだ来ていないので、**猶予を短くして
  判定する**（`HANDSHAKE_GRACE_MS` ではなく `NETWORK_CHANGE_GRACE_MS = 10_000`）。
- 権限: `ACCESS_NETWORK_STATE` は既に宣言済み。**新しい権限は不要**。

**効果**: 「Wi-Fi からモバイルに切り替えたら繋がらない」が、**次にページを開く前に**直る。

### 3.3 プロセス再生成を正常系として扱う（B-2, B-5）

問題は「トンネルが OS 側で生きているか」を安く知る手段が無いこと。
`GoBackend` のインスタンスフィールドはプロセス内なので使えないが、**OS 側には確実な
問い合わせ先がある**。

```kotlin
// data/VpnTunnelProbe.kt（新規）
object VpnTunnelProbe {
    /**
     * 「このアプリの VpnService が今も動いているか」を OS に問い合わせる。
     * ConnectivityManager の VPN ネットワーク一覧に、自パッケージが
     * オーナーである VPN ネットワークが存在するかで判定する。
     */
    fun isOwnTunnelActive(context: Context): Boolean
}
```

- 実装: `ConnectivityManager.allNetworks` から `NetworkCapabilities.TRANSPORT_VPN` を持つ
  ものを絞り、`NetworkCapabilities.getOwnerUid()` が自 UID と一致するかを確認する
  （API 29+。API 26–28 は `NetworkInfo` の `type == TYPE_VPN` と
  `dumpsys` 相当の情報が取れないため、**「不明」を返してフォールバック**する）。
- `onAppForeground()` と `verifyForBackground()` の分岐を次のように変える。

| OS 側のトンネル | メモリ上の `activeTunnel` | 動作 |
|---|---|---|
| 生きている | あり | 通常の検証（現行どおり） |
| 生きている | なし（プロセス再生成） | **作り直さずに「接続中」として復帰**し、検証だけ行う。`getStatistics` は使えない（別インスタンス）ので、**ハンドシェイク時刻は永続化した記録を使い、`isOwnTunnelActive` の結果を疎通の根拠にする** |
| 生きていない | なし | 再確立（現行どおり） |

これで B-5 の「生きているのに壊して作り直す」が消え、
**再生成直後の無駄な DOWN→UP とハンドシェイクのやり直しが無くなる**。

> 補足（正直な制約）: プロセス再生成後は `getStatistics` が使えないため、
> **ハンドシェイクの鮮度による判定はできない**。この状態では
> 「トンネルは生きている（OS がそう言っている）」までしか言えず、
> 実際に通信が流れるかは次のページ読み込みで分かる。UI では
> `VpnReachability.UNKNOWN` ではなく **`TUNNEL_ONLY`（新設）** として
> 「接続中（疎通は未確認）」と正直に出す。

### 3.4 WorkManager の仕事を「守る仕事」と「省電力な仕事」に分ける（A-2）

現行は VPN の周期ジョブが 1 本だけで、制約も無く、未使用時も走る。次のように分ける。

| ジョブ | 目的 | 制約 | 登録条件 |
|---|---|---|---|
| `vpn-health-periodic`（既存） | 消灯中の疎通確認 | `NetworkType.CONNECTED` + **`setRequiresBatteryNotLow(true)`** | プロファイルがあり、かつ **VPN が接続中**（`state.isActive`）のときだけ |
| `vpn-watchdog-periodic`（新規） | プロセスが死んでも VPN を復活させる | `NetworkType.CONNECTED` のみ（電池制約なし） | Always-on VPN がシステム側で有効なときだけ |

- **「VPN を守る」仕事に `BatteryNotLow` を付けるかは思想が分かれる。**
  電池が少ないときに VPN を止めるのは、ユーザーが VPN を選んだ意図に反する。
  そこで **Always-on VPN が有効な場合のみ制約なし**とし、それ以外は `BatteryNotLow` を付ける。
  これは「システムに常時接続を委ねたユーザー」と「アプリ内の自動再接続だけ使うユーザー」を
  区別する自然な線引きになる。
- 登録条件に `state.isActive` を加えることで、**切断中は 15 分ごとに起きない**（A-2 の主因）。
  `state` の変化を購読して `sync()` を呼び直す（`VpnHealthScheduler.observe()`）。

**効果**: 未使用時の起床 96 回/日 → **0 回**。

### 3.5 keepalive を状況に応じて緩める（A-4・任意設定）

既定は 25 秒のまま（NAT 越えの正しさを優先）。設定に **「省電力モード」** を追加し、
有効時のみ keepalive を **60 秒** にする。

- 60 秒は「一般的な UDP NAT のタイムアウト（30 秒〜）より長い」ため、
  **NAT が厳しい回線では切れる可能性がある**。設定の説明文に明記し、既定 OFF。
- 通信量: 0.25 MiB/日 → 0.10 MiB/日。

### 3.6 画面消灯を検知して即座に間引く（A-1 の直接修正）

`HalfBrowserApplication` で `ACTION_SCREEN_OFF` / `ACTION_SCREEN_ON` を受ける
`BroadcastReceiver` を登録（`Context.registerReceiver`、`RECEIVER_NOT_EXPORTED`）。

- `SCREEN_OFF` → `VpnController.onScreenOff()` → ポーリングを背面モードへ。
- `SCREEN_ON` → `onScreenOn()` → 前面モードへ戻し、**即座に 1 回検証**する
  （ユーザーが画面を点けた瞬間に「繋がっていない」ことが分かるように）。

**これは A-1 の本質的な修正**であり、`onStop()` に頼っていた設計の穴を塞ぐ。

### 3.7 `KeepAliveService` を `START_NOT_STICKY` に（B-6）

Web 通知の即時配信は「ブラウザ画面が開いている間」だけ意味がある。プロセスが殺されたら
再生成せず、次にアプリを開いたときに `LaunchedEffect` が再起動する方が正しい。

### 3.8 変更しないもの（互換性）

- `VpnState` の公開 API（`Connected` / `Disconnected` など）は維持。
  `VpnReachability` に **`TUNNEL_ONLY` を追加**するが、`entries` の末尾に足すので
  既存の `name` ベースの永続化（`VpnHealthStore`）は壊れない。
- 設定 JSON に `vpnPowerSaver`（既定 false）を追加。`ignoreUnknownKeys` + 既定値なので
  既存バックアップは読める。
- 日英の文字列を追加（新規キーは両方に必ず入れる。`LocaleParityTest` が強制）。

## 5. 検証計画

### 5.1 JVM テスト（純関数）

- `nextPollDelayMs`: 前面は 10 秒固定、背面は健全回数で増加、上限 300 秒、
  `STALE`/`UNREACHABLE` で 60 秒に戻る。
- `classify` の `TUNNEL_ONLY` 分岐（プロセス再生成後）。
- `VpnTuning`: 省電力モードで keepalive 60 秒、通常は 25 秒。
- 既存 208 件が全て通ること。

### 5.2 エミュレータでの実測（**数値で示す**）

| 検証 | 方法 | 合格条件 |
|---|---|---|
| 消灯中の呼び出し削減 | `adb shell dumpsys batterystats` の CPU 時間と、`logcat` に仕込んだカウンタで 10 分間の `getStatistics` 回数を比較 | 現行比 **80% 以上削減** |
| ネットワーク切替 | `svc wifi disable/enable` と `svc data` を切り替え、`logcat` で再接続時刻を確認 | 切替から **15 秒以内**にハンドシェイク再開（または「接続中（疎通未確認）」表示） |
| 画面消灯 → 点灯 | `input keyevent KEYCODE_SLEEP/WAKEUP` | 点灯直後に 1 回検証が走る |
| プロセス再生成 | `am kill`（キャッシュ状態で）→ アプリ再開 | **DOWN→UP が発生しない**（生きているトンネルを壊さない） |
| 未使用時の起床 | 切断状態で 30 分放置 → `dumpsys jobscheduler` | VPN 関連ジョブが **登録されていない** |
| 省電力モード | 設定 ON で接続 → `wg show` 相当（`getStatistics`）で keepalive 間隔を確認 | 60 秒 |

### 5.2.1 実測結果（2026-11-11、エミュレータ API 34、debug ビルド）

`VpnController.verifyNow()` に debug 限定のカウンタログ（`adb logcat -s VpnPoll`）を仕込み、
推測ではなく回数を数えた。

| 検証 | 実測値 | 判定 |
|---|---|---|
| 前面（画面表示中）60 秒 | **6 回**（10 秒間隔） | 設計どおり |
| **画面消灯 180 秒** | **3 回**（60 秒間隔） | v1.8.0 なら 36 回。**92% 削減**（計画の見積もりと一致） |
| 画面点灯直後 | 即座に 1 回 + 以降 10 秒間隔 | 設計どおり |
| Wi-Fi 切断 / 復帰 | `network changed; re-verifying (state=Connected)` を両エッジで記録 | イベント駆動で動作 |
| プロセス再生成（force-stop → 起動）×3 | 3 回とも 1 回で UP、失敗なし | 設計どおり |
| 接続中のジョブ制約 | `Requires: ... batteryNotLow=true` | 設計どおり |
| 切断後のジョブ | debug アプリの VPN ジョブ **0 件** | 設計どおり（v1.8.0 は 96 回/日 起きていた） |
| 省電力モード ON | `tunnel config: keepalive=[60] mtu=1280` | 設計どおり |
| 省電力モード OFF | `tunnel config: keepalive=[25] mtu=1280` | 設計どおり |

**実測で見つかって修正した問題**

1. `getOwnerUid()` は API **30**（計画では 29 と書いていた）。lint の `NewApi` が検出。
   API 29 で `NoSuchMethodError` になるところだった。ガードを `VERSION_CODES.R` に修正。
2. 再生成直後の自動再接続が `UNABLE_TO_START_VPN` で 1 回失敗していた
   （VpnService の起動が非同期なため）。ネットワーク変化の検知が起動直後にも走ることで
   顕在化しやすくなった。`bringUpWithRetry`（この理由のみ最大 3 回、線形バックオフ）を追加。
3. `onAppForeground` が `visible = true` を直接書いており、背面バックオフ中に前面復帰しても
   古い長い間隔のままだった。`onVisible()` 経由に統一。
4. 失敗ログが `BackendException` の理由を捨てていて原因究明できなかった。理由を含めるよう修正。

### 5.2.2 独立監査で見つかった問題と修正

実装後に別コンテキストの監査エージェントが読み取り専用でレビューした。**リリース不可**の判定を
受けた 2 件を含め、以下をすべて修正した。

| 重大度 | 問題 | 修正 |
|---|---|---|
| 1 | `Application` の `Dispatchers.Default` 上で `WorkManager.getInstance()` を呼び、WorkManager の単一スレッド初期化とデッドロックしうる（`runCatching` は `launch` の例外を捕まえないため**静かに全 VPN ジョブが未登録**になる） | スコープを `Dispatchers.IO` に変更 |
| 1 | `adoptExistingTunnel` の `TUNNEL_ONLY` 分岐が `activeTunnel` を設定しないため、直後の検証が `UNKNOWN` で上書きし、10 秒で消えて再検証されない | `runBlockingVerify` が `activeTunnel == null` のとき OS に問い合わせる。さらに純関数 `VpnHealthRules.publish` を導入し、`UNKNOWN` が `TUNNEL_ONLY` を上書きしないようにした |
| 2 | `VpnHealthWorker` のガードから `vpnAutoConnect` を落としたことで、「起動時に必ず接続」ON＋「再接続」OFF のユーザーのプロセス再生成後復旧が消えた（v1.8.0 からの退行） | ガードを旧条件に戻し、`autoReconnect` の意味だけ分離 |
| 2 | `visible` の read-modify-write を複数スレッドから実行（消灯中に前面レートへ戻りうる） | `AtomicBoolean` 2 つ（`foreground` / `screenOn`）に分離し、`visible` を導出プロパティに |
| 2 | `poller` の二重起動（省電力の劣化） | `pollerLock` で start/stop/restart を直列化。`synchronized` の再入と `return@synchronized` が**そのラムダだけ**を抜けることは、一時テストを書いて実行し確認した（確認後に削除。恒久的なテストとしては残していない） |
| 2 | `NetworkWatcher.stop()` が未使用 | `start()` が成否を返し、成功時のみ保持。寿命をコメントで明示 |
| 2 | 省電力トグルが「起動時に必ず接続」カード内で意味が食い違う | 専用カードへ移動し、「次に接続したときから反映」を明記 |
| 2 | `NETWORK_CHANGE_GRACE_MS` が最初の 10 秒しか効かない | `maxOf(connectedAt, networkChangedAt)` を猶予起点に |
| 3 | `adoptExistingTunnel` のコメントが実装と矛盾 | 実装に合わせて書き直し |
| 3 | `getOwnerUid()` の API レベル記述（実装は 30） | コメントと本設計書を 30 に修正 |

| 3 | `checkedAt` が更新されず「最終確認」が止まる | 60 秒スロットルで公開 |
| 3 | `MAX_BACKOFF_STEPS` の二重定義 | `VpnHealthRules` に一本化 |
| 3 | 省電力の文言が「モバイル通信では」だが実装は接続種別を問わない | 文言を修正（日英） |

### 5.2.3 再監査（修正後）の結果

修正後に同じ監査エージェントへ再レビューを依頼した。**重大度 1 はゼロ**、テスト 223 件緑・lint 0 errors。
残った重大度 2 のうち実害のある 2 件を追加修正した。

| 重大度 | 問題 | 修正 |
|---|---|---|
| 2 | adopt 分岐が `activeTunnel` を立てないため、以後の `connect()` が既存トンネルを落とせず、復旧に失敗しうる | adopt 時にも代理ハンドルを登録（`ActiveTunnel.adopted = true`）。統計は読めないので検証は probe 経路のまま |
| 2 | `NETWORK_CHANGE_GRACE_MS`（10 秒）が `classify` の 45 秒猶予より短く、実質デッドコードだった | `classify(snapshot, now, graceStartOverride)` を追加し、猶予起点を `maxOf(connectedAt, networkChangedAt)` に。**猶予窓とセッション判定を分離**（接続後のハンドシェイクはネットワーク変化前でも有効な証拠） |
| 2 | `state.collect` が共有 IO スレッドを 1 本恒久占有 | `Dispatchers.IO.limitedParallelism(1)` の専用スレッドに |
| 3 | 前面復帰時に `verifyNow` が二重実行（ネイティブ呼び出し 2 回） | `onVisible(verify = false)` で一本化 |
| 3 | `connect()` 内の `startPolling()` がロック外 | `restartPolling()` に統一 |

| 3 | 省電力カードの見出しとスイッチ名が同一文言 | カード見出しを「電池 / Battery」に |
| 3 | コメントの不正確さ（ワーカーのキャンセル、probe の呼び出し頻度） | 実装に合わせて修正 |

追加したテスト: `classify` の猶予上書き 3 件（猶予の再武装、短縮しないこと、ハンドシェイクが優先すること）。

**未解決（正直な記録）**: `VpnController` 自体をインスタンス化するテストは無い（Robolectric 等が
依存に無く、`Context` / `GoBackend` / `VpnService.prepare` への依存が大きい）。判断ロジックは
`VpnHealthRules` の純関数へ切り出してテストしているが、**配線（adopt → verify → publish の経路）は
コードレビューとエミュレータでの動作確認で担保している**。`tunnelProbe` の注入点は用意したが、
現状テストからは使っていない。

### 5.3 実機でしか確認できないこと（正直な記録）

- **実際に画面消灯中にハンドシェイクが維持されるか**は、エミュレータのユーザーネットでは
  検証できない（v1.8.0 と同じ制約）。実機＋実サーバーでの確認が必要。
- Doze モード（`adb shell dumpsys deviceidle force-idle`）中の挙動はエミュレータで
  ある程度再現できるが、実機のメーカー独自最適化は再現できない。

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| `NetworkCallback` が頻発して再接続ループになる | 1.5 秒デバウンス + 既存の `AUTO_RECONNECT_MIN_INTERVAL_MS`（30 秒）を併用 |
| 背面ポーリングを 300 秒まで間引くと、壊れてから最大 5 分気づかない | ネットワーク変化と画面点灯で即時検証するので、実害は「切替も画面点灯も無いまま壊れた」場合のみ。これは許容（電池とのトレードオフ） |
| `TUNNEL_ONLY` の追加で既存の `when` が網羅性エラーになる | コンパイルエラーとして検出されるので、漏れなく対応する（意図的にこの設計） |
| API 26–28 で `getOwnerUid()` が使えない | `VpnTunnelProbe` が `UNKNOWN` を返し、現行どおり再接続にフォールバック（安全側） |
| 省電力モードで NAT が切れる | 既定 OFF、説明文に明記、`STALE` 検知時は通常どおり再接続 |
